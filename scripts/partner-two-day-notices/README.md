# Two-day course signup notifications

Scope: existing `/2days-botsclass/`, existing `aligor-2days-botsclass` D1 `signups` table and the existing partnership webhook. No migration, fee change, actual payment confirmation, old reservations replay, or customer messages outside this course. Dates remain provisional as shown on the page.

- Worker sends the owner Telegram alert and a reference-only authenticated webhook after the atomic D1 insert. Test mode, form rejects and normalized-phone duplicates send nothing.
- The existing Hermes receiver dispatches the new event to `two_day_signup_notice.py`. The module obtains exactly one pending-payment record over the authenticated, no-cache Worker route and passes it to SpiderMan's existing WhatsApp transport. Customer and partner are logged independently in a new local SQLite ledger; a transport result without confirmation is not blindly resent. A single invalid/blocked channel does not prevent attempting the other one. Jason sees only the first learner name, booking number, seats, amount and timing; no student phone, billing data or bank account.
- Customer template: original course/date/venue status, server-calculated amount, existing approved bank details, booking reference as payment remark, and the existing WhatsApp receipt destination. Explicit WhatsApp consent is collected on the form when notifications are enabled.

## Release checklist (real sends only after Adrian approves)

1. Validate the existing registered WhatsApp sender and exact partner number, inbound tunnel routing and invalid-auth rejection. Ensure neither channel is being polled for signups. Check the approval covers the three routes and templates; do not send a test to Jason or real registrants.
2. Stage `receiver.patch` against the installed `~/.hermes/scripts/partner_signup_webhook.py` in a private temp directory, together with the new module, require `shasum -a 256 -c receiver-base.sha256` against the staged original before using `git apply --unidiff-zero receiver.patch`, then run the unit tests and legacy receiver tests; preserve the original half-day routing. Back up the existing receiver script outside the project before atomic replacement; do not alter the existing half-day scope or secret. Set up a private `~/.hermes/state/aligor-two-day-signups/scope.json` (`0700` parent, `0600` file) with `sender: spiderman`, the pinned `partner` JID, and `notBefore` set to the approved UTC cutover timestamp. Retain the ledger for any subsequent update. The receiver fails closed when that file is absent or the scope is incorrect.
3. Restart only the already-loaded `com.aligor.partner-signup-receiver`, verify a new PID and invalid-auth rejection locally and over its existing HTTPS tunnel; verify the old handler continues to respond. Do not touch the tunnel config unless necessary and separately approved. A nonexistent/invalid reference must never send. The new lookup is only usable after deploying the Worker.
4. Follow repository SOP: fetch/rebase, test again, then approved push only. `PARTNER_TWO_DAY_NOTIFICATIONS=1` in `wrangler.jsonc` activates dispatch on the deployed Worker. Reuse the existing Worker webhook bindings, do not write production secrets or submit synthetic production registrations. Check Cloudflare build and live form on both domains, then verify unauthorized lookup and authenticated absent-reference rejection. First real sends should be checked independently in the ledger, in the exact WhatsApp chat and in Telegram. Report `accepted` or `uncertain` separately from `verified`.
5. To disable future notifications, remove the switch via the same GitHub workflow. To immediately stop only the new receiver sends, remove its authorized `scope.json` from the receiver state folder without deleting its ledger. Do not replay historical or uncertain notices as a deployment test.
